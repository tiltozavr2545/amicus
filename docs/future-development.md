# Future Development: Amicus (ранее «Круг»)

Всё, что сознательно отложено за пределы MVP (0.1), чтобы не утонуть на старте. См. основной план в [project-brief.md](project-brief.md).

Возвращаться к этому списку стоит только после того, как MVP заработал целиком (прошли Этап 5 из дорожной карты).

---

## Ближайший план (простые фичи, планирует реализовать)

1. **Переключение языка в настройках приложения** — переключатель языка локали на экране настроек (рядом с тумблерами уведомлений), по умолчанию системная локаль. Выбор сохраняется в `shared_preferences`.

2. **Локализация push-уведомлений** — сейчас текст уведомлений (о новых постах, комментариях, избранном и т.д.) отправляется на английском. Нужно хранить шаблоны уведомлений в ARB-файлах и при отправке через `notification_outbox` / Firebase выбирать текст по локали пользователя.

## Второй этап (более сложные фичи)

1. **Комнаты (Rooms)** — Приватные под-пространства внутри общего круга — изначально были частью общей идеи проекта, но вынесены за пределы MVP, чтобы не увеличивать объём первой версии.

   **Механика:**
   - Создать комнату может любой пользователь.
   - Комнату наполняют только те, кого создатель туда добавил (из числа своих Connections).
   - У комнаты своя изолированная лента — посты, помеченные «только для этой комнаты», не попадают в общую ленту и не видны вне комнаты.
   - Пост можно опубликовать: (а) в общую ленту, (б) в одну или несколько комнат сразу.

   **Модель данных (черновик):**

   | Сущность | Ключевые поля | Комментарий |
   |---|---|---|
   | **Room** | id, name, creator_id, created_at | Комната |
   | **RoomMember** | room_id, user_id, joined_at | Кто состоит в комнате (many-to-many) |
   | **PostTarget** | post_id, room_id (nullable) | Куда опубликован пост: NULL = общая лента, иначе — конкретная комната. Один пост может иметь несколько строк (несколько комнат) |

   Когда дойдёт очередь до этой фичи — `Post` из MVP нужно будет связать с `PostTarget` вместо прямой видимости через Connections.

   **Отдельный этап дорожной карты (после MVP):** создание комнаты, добавление участников, лента комнаты, выбор при публикации — куда отправить пост.

2. **Загрузка GPS-треков (маршруты бега/вело, как в Strava)** — Возможность записать маршрут пробежки/велозаезда через GPS телефона или загрузить готовый трек-файл (GPX/TCX/FIT — форматы, которыми оперируют Strava, Garmin и большинство спортивных часов), с последующим отображением маршрута на карте в посте.

   **Механика (черновик):**
   - Запись трека на устройстве (фоновый GPS-трекинг во время активности) либо импорт готового файла.
   - Разбор трека → ряд координат (lat/lon/timestamp, возможно высота) + агрегаты (дистанция, длительность, средняя скорость/темп).
   - Отображение маршрута на карте в посте — нужен картографический SDK (Google Maps / Mapbox / что-то на OpenStreetMap) — у каждого свои лимиты бесплатного тарифа и стоимость, выбор отдельным вопросом.

   **Модель данных (черновик):**

   | Сущность | Ключевые поля | Комментарий |
   |---|---|---|
   | **Route** (или Activity) | id, post_id, type (run/ride), distance_m, duration_s, started_at | Агрегаты маршрута, привязка к посту |
   | **RoutePoint** | route_id, seq, lat, lon, elevation_m?, recorded_at | Точки трека — либо нормализовать так, либо хранить сырой GPX/FIT-файл в Storage и парсить на лету, вопрос открыт |

   **Открытые вопросы:**
   - Хранить трек как файл в Storage и парсить на лету, или нормализовать в таблицу точек в БД — компромисс между простотой и возможностью запросов/агрегации по трекам.
   - Какой картографический сервис использовать (стоимость, лимиты бесплатного тарифа, доступность на Android без лишней настройки).
   - В первой итерации — только загрузка готового файла, или сразу и live-запись GPS во время самой активности?

3. **Доработка интерфейса/UI-полировка** — сверх того, что сделано на Этапе 5 (сейчас функционально, но не более)

4. **Локализация новостного аккаунта Amicus** — сейчас посты от новостного аккаунта (новые фичи, дайджесты, новости приложения) приходят только на русском. Нужно создать отдельный контент для каждой локали (или хотя бы для анлийской), отправлять посты от одного аккаунта, но с текстом на локали конкретного пользователя.

5. **Deep link для подтверждения email** — сейчас ссылка из письма ведёт на статическую страницу-подтверждение на GitHub Pages (`site_url` в `supabase/config.toml` → `https://tiltozavr2545.github.io/amicus/`, исходник — ветка `gh-pages`, один `index.html`), потому что само подтверждение засчитывается на стороне Supabase ещё до редиректа. Это решает проблему непонятного лендинга (раньше вело прямо на GitHub-репозиторий), но открывать сразу экран приложения было бы удобнее — требует настройки custom URL scheme / Android App Links и обработки в `supabase_flutter`, отдельная задача не для MVP

6. **Web-версия приложения** — Flutter Web или отдельный frontend на React/Vue

7. **iOS-версия приложения** — MVP (0.1) задеплоен только на Android (Google Play, Internal Testing track). iOS-сборка сознательно отложена — изначально из-за dev-машины на macOS 12.7.6 (Xcode требует macOS 14+, см. CLAUDE.md), теперь просто как отдельная задача после портфолио-релиза на Android.

   Когда дойдёт очередь:
   1. Обновить dev-машину до macOS 14+ (или собирать на другой машине/CI) и установить Xcode.
   2. Apple Developer аккаунт (платный, $99/год — единственная точка, где потребуются деньги).
   3. Прогнать `flutter create --platforms=ios` конфигурацию (уже подключена изначально) через `flutter run`/`flutter build ios` на реальном устройстве или симуляторе, поймать платформенные баги, которых не было на Android.
   4. Xcode archive → App Store Connect → TestFlight, добавить себя/друзей как тестеров.

8. **Знакомство через NFC** — как альтернатива invite-ссылке/QR — совсем далёкая идея, не приоритет

9. **Полный аудит политики конфиденциальности и интеграция согласия в UI** — сейчас privacy policy статическая на GitHub Pages, согласие на email-подтверждение только, без опций в UI

10. **Переезд с Supabase на собственный сервер (ASP.NET Core + PostgreSQL)** — Не гипотеза, а решённый вопрос: рано или поздно вся база данных переедет с Supabase на собственный личный сервер — просто не для 0.1, это избыточно на старте. У тебя уже есть опыт с ASP.NET Core + PostgreSQL (по сути то же самое, что ты делал в лабе с TransferScout), backend можно будет переписать на нём. RLS-политики сейчас пишутся как чистый Postgres SQL — переносить логику доступа при миграции не придётся, только слой Auth/Storage/Realtime.

## Идеи на потом (вероятно не будут реализованы, но есть чтобы возможно потом к ним вернуться)

- **QR-сканирование как второй способ знакомства** — в дополнение к invite-ссылкам

- **Интеграция с существующими соцсетями (Instagram, TikTok и т.д.)** — возможность подключить аккаунт, перенести посты (с фото/видео) на собственную стену в Amicus, однократная синхронизация или фоновая периодическая. Синхронизация друзей на стену как опция (кто попадает из подписок инсты в Connections или отдельный список). Лечит основное возражение к отказу от соцсетей: контент друзей остаётся, но в первой заблокированной для всех остальных вкусе

- **Счётчик просмотров поста** — Формулировка задачи «своеобразная» (по словам автора) — если когда-нибудь дойдут руки, перед началом реализации нужно уточнить, как именно считать просмотр (при показе карточки в ленте / при полном раскрытии / только уникальные юзеры / что с повторными просмотрами и т.п.), не додумывать самостоятельно

- **Push-уведомления о реакциях на свои посты** — отдельная от уже реализованного (посты — 0.12.0, комментарии/ответы — 0.14.1) кусок той же идеи push-уведомлений; свой `kind` в `notification_outbox`, триггер на `reactions` вместо `posts`/`comments`

- **Видео-сообщения («кружочки», как в Telegram)** — Круглые видео-сообщения, записываемые с камеры прямо в приложении — как альтернатива/дополнение к фото в посте или комментарии.

  **Механика (черновик):**
  - Запись через камеру устройства (обычно фронтальную), с ограничением по длительности (например, 60 сек, как в Telegram).
  - Круглая маска — скорее клиентское отображение (`ClipPath`/оверлей), а не перекодировка самого видеофайла в круглую форму.
  - Хранение — Storage (тот же бакет, что и фото, либо отдельный), видимость по тем же правилам приватности, что уже действуют для фото/аватарок (Connections-only).

  **Открытые вопросы:**
  - Отдельный тип вложения к посту, или только к комментарию (либо и то, и другое)?
  - Лимит размера/длительности и нужна ли перекодировка/сжатие на клиенте перед загрузкой.
  - Автовоспроизведение в ленте (со звуком или без) — вопрос UX, решать отдельно.

- **Настройки приватности** — кто видит список твоих контактов (частично всплыло в аудите — см. «Первый аудит» в разделе «Исправлено из аудита кода» ниже: в 0.4.0 чтение `users` и `reactions` сужено до «только свои связи / только свои строки», но сам вопрос о видимости списка контактов остаётся открытым)

- **Полноценная модерация и жалобы** — Модерация, жалобы, блокировка знакомого (частично: простая обратимая блокировка — взаимное скрытие постов без разрыва Connection, без жалоб и модерации — реализована в 0.9.0, см. CHANGELOG.md; полноценная модерация/жалобы остаются здесь)

## Исправлено из аудита кода

### Первый аудит (закрыт в 0.4.0)

Полное ревью проекта (RLS, Storage-политики, клиент, секреты, вся история git) прошло чисто: критичных дыр нет, секретов в репозитории и истории git нет, `service_role`/secret-ключ в клиенте не используется, anon-ключ публичный by design. Сильные места — `security definer` + `set search_path` на функциях, `for update` против гонки при активации инвайта, канонический порядок пар, `revoke execute … from anon`, лимит размера + allow-list MIME, `enable_anonymous_sign_ins = false`, email-подтверждение, `additional_redirect_urls = []`.

- ~~**Утечка соцграфа через реакции**~~ ✅ Политика SELECT на `reactions` была широкой — на любом видимом посту через API вытаскивался `user_id` **всех** реагировавших, а через общедоступную тогда `users` он мапился в имя. Теперь SELECT на `reactions` отдаёт только собственные строки (`user_id = auth.uid()`), а публичные счётчики на пост считает `security definer`-функция `reaction_summary(uuid[])`: возвращает только числа (like/neutral/dislike) плюс собственную реакцию вызывающего, без чужих `user_id`. Миграция `20260712100000_scope_profile_and_reaction_visibility.sql`.

- ~~**Вся адресная книга читается любым залогиненным**~~ ✅ `users` SELECT был `using (true)` — любой видел имена/аватары/`id` **всех**. Теперь SELECT на `users` = «своя строка ИЛИ мой Connection». Перечислить всю адресную книгу через API больше нельзя. Миграция `20260712100000_scope_profile_and_reaction_visibility.sql`.

- ~~**Файлы аватарок читались любым залогиненным**~~ ✅ Storage-политика проверяла только `bucket_id='media' AND foldername[1]='avatars'` — любой залогиненный мог скачать чужое фото по пути `avatars/{uuid}/...`. Теперь storage-политика зеркалит правило `users`: аватарку видно только себе и своим Connections. Проверено RLS-тестом на живой БД. Миграция `20260712120000_scope_avatar_storage_visibility.sql`.

### Второй аудит (закрыт в 0.11.0)

Ревью ветки 0.8.1→0.10.3 прошло не чисто. Урок: почти всё найденное появилось не из-за плохой политики, а из-за **дuplирования правила видимости**. Правило «чьё содержимое мне видно» жило в четырёх местах, mute/block из 0.9.0 доехали не до всех, и две отставшие копии оказались настоящими дырами.

- ~~**Мелкая закалка**~~ ✅ Нет лимита длины на текст поста/комментария — добавлены `check (char_length(text) <= 5000)` + счётчик символов в UI. Сырые тексты исключений в сообщениях об ошибках заменены на человекочитаемые формулировки. Закрыто в 0.9.1.

- ~~**Правило видимости размножено на четыре копии, две отстали от mute/block**~~ ✅ Было инлайн в политике `posts`, инлайн в `reaction_summary()`, функцией `is_comment_author_visible()` и инлайн в storage-политике на фото постов. 0.9.0 обновила не все: заблокированный получал через `/rpc/reaction_summary` живые счётчики реакций скрытых от него постов. Все четыре сведены в одну `is_author_visible(uuid)`; впредь правило меняется в одном месте. Миграции `20260726120000`, `20260726130000`. **Аватарки сужать не надо** — блок не рвёт Connection, заблокированный остаётся в списке знакомых.

- ~~**Definer-хелперы отвечали на чужие вопросы**~~ ✅ Каждая функция в открытой схеме — эндпоинт PostgREST, поэтому грант `authenticated` = «зови с любыми аргументами». `is_blocked_pair(a, b)` не привязывала аргументы к `auth.uid()` и сообщала, заблокировали ли друг друга **посторонние**; `comment_author(uuid)` отдавала автора любого комментария мимо RLS. Первой снят грант (звалась только изнутри другой definer-функции), вторая свёрнута в булеву `is_author_of_comment_visible(comment_id)` и удалена. Миграция `20260726140000`.

- ~~**`delete_own_comment()` ошибалась в опасную сторону**~~ ✅ `if v_author <> auth.uid()` при `auth.uid()` = NULL даёт NULL, `if` не срабатывает, и функция проваливается в удаление. Плюс гонка: проверка «есть ли ответы» и hard delete шли разными операторами. Теперь явный guard + `is distinct from` + `for update` до проверки. Миграция `20260726150000`.

- ~~**Серверное состояние было клиентски записываемым**~~ ✅ Дефолтные гранты Supabase дают `authenticated` писать все колонки, а INSERT-политики про них молчали: комментарий вставлялся сразу заглушкой (`deleted_at`), а пост — с датой 2099 (`created_at`). Обе колонки прибиты в `with check` (`deleted_at is null`, `created_at = now()`). Миграции `20260726160000`, `20260726190000`.

- ~~**Сырой текст ошибки при активации инвайта**~~ ✅ Стабильные SQLSTATE (`PT404`/`PT409`/`PT422`) + текст из ARB; всё неизвестное — общее сообщение (без сырого текста исключений). Миграция `20260726170000`.

- ~~**Стоимость RLS росла со всей таблицей**~~ ✅ `security definer`-функцию планировщик не инлайнит, поэтому `using (is_author_visible(author_id))` — вызов на каждую строку скана. Лента на 2000 постов **217 мс** → **3.5 мс** (62×); счётчики комментариев при 1000 комментариев **115 мс** → **5 мс** (23×). Правило зависит только от вызывающего, спрашивается раз на запрос через `visible_author_ids()` + хэшируемый `IN (SELECT ...)`. Миграция `20260726180000`.

- ~~**Нет клиентского таймаута на сетевые запросы**~~ ✅ Замечено при аудите, но не исправлено сразу: отправка комментария в режиме полёта висела спиннером ~3.5 минуты, прежде чем упасть в снекбар — ветка ошибки была корректной, но пользователь всё это время не понимал, что происходит. `.timeout(networkTimeout)` (12 сек, `lib/shared/network_timeout.dart`) добавлен на все вызовы Supabase; `TimeoutException` ловится тем же общим `catch`, что и любую другую сетевую проблему — новых ARB-строк не потребовалось. Закрыто в 0.11.1.

- ~~**Счётчики комментариев считались на клиенте**~~ ✅ Отложено сознательно при аудите — правка клиентского пути данных без покрытия тестами. Сервер отдавал по строке на каждый видимый комментарий (сотни строк, ~40 КБ) только чтобы их сосчитать на клиенте. `comment_summary(uuid[])`, `security invoker` (в отличие от `reaction_summary()` не дублирует правило видимости — RLS-политика `comments` уже фильтрует нужные строки сама). Миграция `20260817120000_add_comment_summary_function.sql`. Закрыто в 0.11.1.

- ~~**Приватность бакета `media` не подтверждена**~~ ✅ Storage-RLS осмыслен только если бакет `Private`; клиент это предполагает (signed URLs), но раньше подтвердить можно было только глазами в дашборде. Проверено прямым запросом к `storage.buckets` через Management API: `public = false`, лимит 20 МБ, allow-list `image/jpeg,png,webp,heic,heif`. Закрыто в 0.11.1.

### Третий аудит (закрыт в 0.13.2)

Не по конкретному подозрению, а самостоятельная проверка «с нуля»: два
прогона подряд, второй намеренно не опирался на выводы первого. Первый разобрал
весь проект (RLS, миграции, Dart-клиент); второй — уже диф первого, свежим
взглядом. Урок ближе ко второму аудиту, чем к первому: почти всё найденное
жило в самых новых на тот момент миграциях (системный аккаунт, избранное,
push-уведомления — 0.12.0/0.13.0/0.13.1, то есть уже **после** урока 0.11.0
про единое правило видимости) и было тем же классом ошибки в новой одежде —
не потому, что урок забыт, а потому что каждая новая фича по отдельности
казалась слишком маленькой, чтобы через неё заводить общий хелпер.

- ~~**Избранное давало пуш о постах не-Connection**~~ ✅ `favorite_users.favorite_id`
  никогда не проверялся на реальный Connection (сознательно, как у mute/block) —
  но триггер `enqueue_post_notifications()` использовал это как единственное
  условие для мгновенного пуша, не спрашивая `is_author_visible()`. Можно было
  добавить в избранное кого угодно, включая того, кто тебя заблокировал (блок
  не рвёт Connection), и получать «автор запостил» по имени и id поста в обход
  ленты. Миграция `20260819100000`.

- ~~**Пуш-токен утекал между аккаунтами на одном устройстве**~~ ✅ `device_tokens`
  не чистился при выходе (`signOut()` был fire-and-forget, без удаления
  токена), а PK `(user_id, fcm_token)` не давал новой записи перезаписать
  старую — после смены пользователя на общем телефоне прежний продолжал
  получать пуши на устройство, которым уже не владеет. `unregisterDevice()`
  теперь чистит свою запись до выхода, пока сессия ещё жива (RLS-проверка
  `user_id = auth.uid()` иначе не пройдёт). Заодно поймана гонка в
  собственном фиксе: `ref.onDispose()` после `await` кидает
  `UnmountedRefException`, если провайдер уже пересоздан (выход случился, пока
  висел системный диалог разрешений) — подписка на `onTokenRefresh` в этом
  случае оставалась неотменённой. Добавлена проверка `ref.mounted`.

- ~~**Гонка блокировок в триггере уведомлений могла ронять сам пост**~~ ✅ Цикл
  по подписчикам брал построчную блокировку `pending_post_counts` без
  `order by` — два одновременных поста от авторов с общими знакомыми могли
  захватывать эти блокировки в разном порядке, и Postgres убивал одну из
  транзакций целиком (не только уведомление — сам `insert` в `posts`). Порядок
  зафиксирован (`order by viewer_id`). Миграция `20260819100000`.

- ~~**Владелец поста не мог ответить на видимый ему чужой комментарий**~~ ✅
  SELECT-политика `comments` научилась показывать чужие комментарии владельцу
  поста (0.13.1), INSERT-политика — нет: кнопка «Ответить» была видна, но
  вставка падала под RLS. Добавлено то же исключение в INSERT. Миграция
  `20260819120000`.

- ~~**`reactions` не получила защиту, которую давно получили `posts`/`comments`**~~ ✅
  Тем же путём (существование чужой строки различимо по конфликту 23505 против
  успеха) можно было прощупать `id` реакции; отдельно — `post_id` был вообще не
  закреплён на UPDATE, и свою реакцию можно было переставить на любой пост,
  включая скрытый — по «успех с пустым ответом» против «ошибка внешнего ключа»
  опять читалось «существует ли пост». `id`/`created_at` закрыты грантом на
  INSERT (миграция `20260819130000`); `post_id`/`id`/`created_at` на UPDATE —
  BEFORE-триггером, который тихо возвращает старые значения вместо ошибки
  (миграция `20260819150000`) — грант вместо триггера сломал бы легитимное
  переключение типа реакции (клиентский upsert без `onConflict` шлёт `post_id`/
  `user_id` в SET на каждый вызов, не только `type`), проверено вживую.

- ~~**Правило видимости повторено инлайн ещё дважды**~~ ✅ Проверка mute/block
  была переписана вручную в пяти новых местах вместо переиспользования
  `is_blocked_pair()` — заведена симметричная `has_muted()` (миграция
  `20260819110000`). Проверка «есть ли Connection» — в трёх местах, включая
  политику `users` — заведена `are_connected(a, b)`, но **не выдана наружу**,
  как и `is_blocked_pair` после 0.11.0: для единственного места, где нужен
  прямой грант (сырая RLS-политика `users`), сделана безопасная обёртка
  `is_connected_to_caller(other)` с одним аргументом, привязанным к
  `auth.uid()` — иначе получилась бы ровно та дыра, что раньше была у
  `is_blocked_pair(a, b)` до 0.11.0. Миграция `20260819160000`.

- ~~**`created_at` у `favorite_users`/`device_tokens` был как у `posts` до
  0.11.0**~~ ✅ Дефолтный грант Supabase на новых таблицах 0.13.1. Закрыто
  грантом на INSERT, не пином по значению — обе таблицы живут upsert'ом без
  `onConflict`, и пин `created_at = now()` сломал бы повторный апсерт (сравнил
  бы дату *первой* вставки с текущим `now()`). Миграция `20260819140000`.

- ~~**`AuthException.message` показывался сырым английским**~~ ✅ Три auth-экрана
  обходили собственную конвенцию проекта — переключаться по коду, не по
  тексту, уже принятую для `PostgrestException`. Заведена `authErrorMessage()`
  (переключение по `AuthException.code`) и 5 новых строк в обоих ARB.

Одна находка второго прогона оказалась ложной: `parent_comment_id`/
`reply_to_id` без проверки, что родитель на том же посте, что и новый
комментарий, — на вид дыра, но уже отклонялась существующим триггером
`comments_enforce_reply_rules` («Parent comment belongs to a different post»),
пропущенным при чтении одних только RLS-политик. Подтверждено симуляцией
эксплойта (отклонён триггером) и легитимного сценария (владелец поста отвечает
на видимый комментарий — работает). Написанная под эту находку миграция
откачена в той же сессии, не выпущена.

Проверено на живой БД тем же способом, что требует CLAUDE.md — RLS-симуляцией
в откатываемой транзакции для каждой находки, включая контрольный
положительный сценарий (чтобы отличить «дыра закрыта» от «сломал вообще
всё»), не глазами. `make verify` чист на обоих прогонах: 80 → 89 тестов (+9 на
`authErrorMessage()`); тестов на сам push-модуль по-прежнему нет —
`FirebaseMessaging.instance` не подменить без инфраструктуры мока Firebase,
которой в проекте нет, а заводить её ради этой правки посчитали
непропорциональным.
