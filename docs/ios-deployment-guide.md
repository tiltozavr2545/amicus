# iOS deployment: build, signing and TestFlight

This is the current runbook for the upcoming 0.19.1, alongside the existing
TestFlight workflow. It does not record live App Store approval or submission
status. Use [Xcode Cloud](xcode-cloud-setup.md) for stable remote archives and
[API automation](app-store-connect-api-automation.md) for a programmatic trigger.

## Prerequisites

- Use the iOS development machine with full Xcode, or Xcode Cloud. The Intel
  macOS 12 Android machine must not run simulators and cannot build the current
  iOS runner with its Flutter 3.32.8 SDK.
- Xcode Cloud pins Flutter **3.47.5** in
  `app/ios/ci_scripts/ci_post_clone.sh`. A local iOS SDK must support the
  committed `FlutterImplicitEngineDelegate` and `FlutterSceneDelegate` APIs;
  use the Cloud pin as the reproducible reference, independently of Android.
- Use a stable supported Xcode and host OS for local distribution. A previous
  beta-host archive was rejected with `ITMS-90111`; a stable Xcode app alone
  did not remove its `BuildMachineOSBuild` stamp. Cloud builds avoid that host.
- Configure an Apple Developer signing identity and the app record for bundle
  ID `com.github.tiltozavr2545.amicus`. Actual account/team access is external
  state; check it before building.
- Supply `app/.env` from `app/.env.example` and the Firebase iOS configuration
  `app/ios/Runner/GoogleService-Info.plist`. Both are gitignored. Never replace
  either with CI placeholder configuration in a distributed build.

## 1. Project configuration

Open `app/ios/Runner.xcworkspace`. `GoogleService-Info.plist` is already
registered in the Xcode project, including its Resources build phase; restore
its bytes from the Firebase app configuration rather than registering it twice.

The project includes `FlutterGeneratedPluginSwiftPackage`; the retained
Podfile also applies Flutter plugin setup and a deployment-target floor of
**iOS 15.0**. Use the dependency integration generated by the selected SDK.
Do not remove the package reference or discard lockfiles as routine setup.
If running CocoaPods manually, run `flutter pub get` in `app/` first, then
`pod install` in `app/ios/`.

`Runner/Info.plist` declares the scene manifest and `SceneDelegate.swift`.
Plugin registration is in `AppDelegate.didInitializeImplicitFlutterEngine`;
the iPad window-control safe-area adjustment is in `SceneDelegate`. Keep them
in step with the iOS Flutter SDK when changing lifecycle integration.

## 2. Build checks

From the repository root, select the actual iOS Flutter executable:

```bash
make FLUTTER=/path/to/ios-flutter/bin/flutter build-ios
```

This is an unsigned compile check with placeholder Supabase values. Its output
is unsuitable for TestFlight or App Store distribution. The Android Intel SDK
pin remains unchanged by this command override.

## 3. Device and simulator verification

Use a physical iPhone/iPad for release validation, including push delivery.
Simulator-only rendering checks are optional on the capable iOS machine;
never launch one on the Intel Android machine. Choose an installed stable
runtime compatible with the selected Xcode rather than copying an old runtime
number from a runbook.

If the simulator hides its software keyboard, disable **I/O → Keyboard →
Connect Hardware Keyboard**. This is a simulator input setting, not a fix in
Amicus. Verify real keyboard behavior separately on a physical device.

Apple supports APNs Sandbox in supported simulator configurations (iOS 16,
macOS 13, Apple silicon/T2 or newer supported setups); saying that APNs never
works in any simulator is incorrect. The project's recorded APNs key is
Production-scoped and this release uses physical-device/TestFlight checks.
See [Apple's Simulator release notes](https://developer.apple.com/documentation/xcode-release-notes/xcode-14-release-notes#Simulator)
and [Firebase's Flutter prerequisites](https://firebase.google.com/docs/flutter/setup?platform=ios).

## 4. Push delivery

The APNs setup was completed previously; do not generate a replacement key
for every release. Check the current Firebase configuration and delivery using
[ios-push-apns-setup.md](ios-push-apns-setup.md). An FCM token or a processed
outbox row alone does not establish delivery. Match Sandbox/Production
credentials to the actual installation environment.

## 5. Icons and launch screens

The authored mark is `app/assets/branding/app_icon.png`. From the repository
root, `python3 scripts/generate-branding.py` (Pillow required) regenerates the
berry Android background layers and opaque iOS icon sizes. It preserves the
Android foreground/monochrome layers and authored mark. Do not recreate the
old gradient icon or apply obsolete 88%/61% artwork scaling instructions.

iOS slots are defined in `app/ios/Runner/Assets.xcassets/AppIcon.appiconset/Contents.json`.
The App Store icon must remain opaque. Launch screens keep their current
neutral backgrounds and retained artwork; a separate launch composition is
an optional design task, not a blocker introduced by this documentation.

## 6. Export compliance

`Info.plist` currently sets `ITSAppUsesNonExemptEncryption` to `false`.
The app uses its existing HTTPS/TLS services; this task adds no encryption.
Reassess the declaration against the actual implementation and Apple's
questions if encryption behavior changes.

## 7. Build the signed IPA

On the iOS machine, use the real Firebase configuration and `app/.env`:

```bash
make FLUTTER=/path/to/ios-flutter/bin/flutter release-ios
```

The target runs `flutter build ipa --dart-define-from-file=.env` with the
committed `ios/ExportOptions.plist` (`app-store-connect`, automatic signing).
Output is `app/build/ios/ipa/`. Signing/provisioning must be available to Xcode.
Alternatively let Xcode Cloud archive on its stable image.

`pubspec.yaml` is the app-version/build source. Runner keeps
`VERSIONING_SYSTEM` disabled and `CURRENT_PROJECT_VERSION` tied to
`$(FLUTTER_BUILD_NUMBER)`; do not enable Cloud's independent build counter.
0.19.1 is not released yet: do not invent a new version merely to follow this
runbook. Confirm actual store build-number availability before an upload.

## 8. Upload to App Store Connect

Upload the signed IPA with Transporter, or use the configured Xcode Cloud
post-action. Check processing/validation results and the embedded version/build.
An uploaded archive is not an approved release. Store text is maintained as a
[listing draft](review/app-store-listing-draft.md); select the correct app
record rather than assuming its marketing name from an old screenshot.

## 9. Get it into TestFlight

Attach the processed build to the intended existing test group and verify its
installation on a physical device. Check sign-in, primary and secondary
navigation, large text, keyboard return, images/zoom, video suspension,
background chat catch-up and notification taps. Keep reviewer credentials
outside the repository and confirm that any existing review fixture still works.

If testers see no available build, check group/build assignment, processing,
compliance and Test Information before rebuilding. A previous initial group
needed its What to Test text saved; that was a recovery observation, not a
mandatory step for every upload. App Store submission and TestFlight testing
remain distinct actions, governed by the current App Store Connect state.
